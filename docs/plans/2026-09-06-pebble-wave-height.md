# Pebble Time 2 波高推定アプリ

## 背景 (Context)

小型船に乗っているとき、いま自分がいる海域の波がどれくらいなのかを、その場で知りたい。
波浪予報は広域・時間粗の値であり、目の前の海況と一致するとは限らない。
「予報は 1.5m だが実際どうなのか」を、手持ちの機材だけで確かめたい。

Pebble Time 2 には IMU が載っており、船の上下動を測れる。
船が波にほぼ追従するサイズであれば、船の鉛直運動は海面の鉛直運動の代理になる。
これは波浪観測ブイ (Datawell、OpenMetBuoy、SFY 等) がやっていることと原理的に同じで、
加速度を周波数領域で2回積分すれば有義波高が求まる。

達成したい状態は「船の上で手を固定して 40秒ほどで、いまの波高が読める」こと。
(内訳: 姿勢が安定するまでの重力方向の収束に約10秒、そこから1セグメント32秒。
起動から初回表示までは約42〜47秒になる。)
腕時計の画面で一目で分かることを最優先し、精度は予報値と見比べて納得できるレベルを狙う。

なお watch には 6軸IMU (LSM6DSOW) が載っているが、**公開 C SDK にジャイロ API は無い**ため、
本アプリは加速度計3軸のみで構成する。この制約が後述の「てこ腕問題」を解けなくしている主因である。

### このアプリが測っているものの限界 (重要)

**測っているのは「時計を置いた場所の上下動」であって「波そのもの」ではない。**
系統誤差は互いに逆向きの2つがある。

**(A) 過小評価 — 船の追従性**

船は自分の船長より短い波には追従せず乗り越えてしまう。
波長が船長の約2倍以上あれば概ね追従するので、追従下限の周期は `T_min ≈ √(4πL/g)`。

| 船長 L | 追従下限周期 T_min | これ以下の周期の波 |
|--------|------------------|------------------|
| 5 m | 2.5 s | 過小評価 |
| 8 m | 3.2 s | 過小評価 |
| 10 m | 3.6 s | 過小評価 |
| 12 m | 3.9 s | 過小評価 |

このため本アプリは **船長 12m 程度までの小型船 (プレジャーボート・釣り船・遊漁船) 専用**とする。
船長は設定項目とし、そこから T_min を計算して、
**推定周期 Tm-1,0 が T_min を下回ったら「短周期の波が主体 — 過小評価の可能性」を画面に表示する。**
(RAO による定量補正は行わない。理由は「却下した案」参照。)

**(B) 過大評価 — 回転運動のてこ腕**

船は剛体なので、回転中心から離れた点の鉛直変位には `距離 × 回転角` が加算される。
ロール(横揺れ)なら中心線からの横距離、ピッチ(縦揺れ)なら船体中央からの前後距離が「てこ腕」になる。

全幅3m (半幅 1.5m) の船で、ロール片振幅ごとの見かけの Hs 寄与:

| ロール片振幅 | 船縁の鉛直変位振幅 | ロール単独の見かけ Hs |
|------------|-----------------|---------------------|
| 5° | 0.131 m | 0.370 m |
| 10° | 0.260 m | 0.737 m |
| 15° | 0.388 m | 1.098 m |

真の Hs = 0.5m の海でロール片振幅15°なら(波とロールが無相関として)、
m0 = (0.5/4)² + 0.3882²/2 = 0.015625 + 0.075361 = **0.090986**
→ **表示 Hs = 4√m0 = 1.206 m (真値の 2.41倍)**。

**これは重力方向への射影 (決定5) では原理的に消せない。** 船縁は実際に上下しているからである。
ジャイロがあればロール角を積分して差し引けるが、SDK に無い。

このため **測定位置を「船のヘリ」から「船体の中央寄り」に変更する** (決定2)。
中心線上ならロールのてこ腕がゼロ、船体中央なら加えてピッチのてこ腕もゼロになる。

**「中央寄り」の許容距離を定量化する。** ロール由来の Hs 寄与は `2√2 · r · sin φ0`。
これを真の Hs に対する誤差 +20% 以内に抑える条件は `r ≤ 0.663 · Hs / (2√2 · sin φ0)`:

| 真の Hs | ロール片振幅 | 許容てこ腕 r |
|---------|------------|------------|
| 1.0 m | 10° | 1.35 m |
| 1.0 m | 15° | 0.91 m |
| 0.5 m | 10° | 0.68 m |
| 0.5 m | 15° | **0.45 m** |

**小さい波・大きいロールほど厳しい。** 目安として **中心線から 0.5m 以内**を推奨とし、
それを超える位置しか無い場合は過大評価を受け入れることになる、と README と初回起動画面に明記する。

### 信号処理パラメータ

| 項目 | 値 | 根拠 |
|------|-----|------|
| 加速度取得レート | **手順2.5 で実測して決める**(10 / 25 / 50 Hz の候補) | 10Hz は電池に有利だが、船底叩き(スラミング)のような衝撃イベントをアンダーサンプリングすると低周波ノイズを生む(SFY 論文の知見)。0〜5Hz の偽エネルギーが少ない方を選ぶ |
| バッチサイズ | 25 サンプル (SDK の `samples_per_update` 上限) | 10Hz なら 2.5秒ごと、25Hz なら 1秒ごとのコールバック |
| デシメーション | 取得レートに応じた箱型平均または FIR ローパス → **2 Hz** | 10Hz の5点箱型平均は 2/4/6/8Hz に厳密な零点を持ち、間引き率5のエイリアス中心と一致するので実は良く効く(後述)。25Hz 以上を選ぶ場合は 13タップ程度の FIR |
| ドループ補償 | `S_a(f_k)` を `|H(f_k)|²` で除算 | 5点箱型平均のパワー応答は 0.25Hz で 0.952、0.4Hz で 0.880、0.5Hz で 0.817。補償しないと短周期側で Hs が最大 9.6% 低く出る |
| セグメント長 | 64サンプル @ 2Hz = **32秒** | ユーザーが姿勢を維持できる上限。Δf = 0.03125 Hz |
| デトレンド | **窓掛けの前に、64点の最小二乗1次トレンドを除去** | 波浪ブイ処理の標準工程。無いと傾き 0.6°/32秒 のドリフトだけで擬似 Hs 0.078m が出る(後述) |
| FFT | 64点 radix-2 複素FFT (虚部0)、float | 192バタフライ ≈ 2000 flops。soft-float でも約 1.1ms。32秒に1回なので問題ない |
| 窓関数 | **周期 Hann 窓**。正規化は PSD 式の `Σw[n]²` で行う | `Σw[n]² = 3N/8` なので、これが 8/3 補正そのもの。**別途 8/3 を掛けてはいけない**(掛けると Hs が 1.633倍になる) |
| ĝ 推定 | 1次IIR。**起動直後は τ=2s、姿勢安定を検出したら τ=30s に切り替える** | τ=30s 固定だと起動時の姿勢変化への追従に90秒かかり、その過渡ドリフトが 1/f⁴ で42倍増幅されて 1m級の偽 Hs を生む |
| ウォームアップ | **ĝ が収束するまではセグメント収集を開始しない**(破棄ではない)。収束判定は「直近2秒の ĝ 方向変化が 1° 未満」。τ=2s なので通常 10秒前後 | 「最初の1セグメントを破棄」にすると初回表示が 64秒後になり、決定6(32秒で暫定値)と矛盾する。収集開始を遅らせる方式なら初回表示は約42〜47秒 |
| 積分帯域 | ビン2 (0.0625Hz) 〜 ビン16 (0.5Hz) | 決定8 |
| ノイズ床 | 静置校正で得た `N_floor` [(m/s²)²/Hz] を **固定定数として** persist に保持 | 決定11。**単位は片側PSD であって標準偏差ではない**(後述の校正手順) |

### 主要な計算式

**単位変換**(これを忘れると `Hs = 4√m0` が成立しない):

```
a[m/s²] = a[mG] × 9.80665e-3
```

**鉛直加速度**:

```
ĝ(t) = LPF(a(t))                            # 起動後15秒 τ=2s、以後 τ=30s
a_vert(t) = dot(a(t), ĝ(t)) / |ĝ(t)| - |ĝ(t)|
```

`|ĝ| < 100 mG` ならセグメント無効(ゼロ除算ガード)。

**セグメント処理**(`spectrum.c` の責務はここまで):

```
1. 線形デトレンド: 64点の最小二乗直線を引いて残差を取る
2. 周期 Hann 窓を掛ける
3. 64点 FFT
4. 片側パワースペクトル密度:
   S_a(f_k) = 2 |X_k|^2 / (fs * Σ w[n]^2)        k = 1 .. N/2-1
5. ドループ補償: S_a(f_k) /= |H(f_k)|^2
```

**Welch 平均と波浪諸元**(`accumulator.c` の責務。**セグメントごとに Hs を出してから平均してはいけない**):

```
S_avg(f_k) = (1/n_seg) Σ_i S_a,i(f_k)          # 有効セグメントのみ

S_z(f_k) = max(0, S_avg(f_k) - N_floor) / (2π f_k)^4     # クランプは除算の前、ビンごと

m0  = max(0, Σ S_z(f_k) Δf)          k ∈ [2, 16]
m₋₁ =        Σ S_z(f_k)/f_k * Δf     k ∈ [2, 16]

Hs     = 4 √m0                        # m0 = 0 なら「凪」表示
Tm-1,0 = m₋₁ / m0                     # m0 = 0 なら周期は `--`
H1/10  = 1.27 × Hs
```

**`N_floor` の定義と校正手順**(単位を間違えると次元が合わない):

`N_floor` は **静置データを本番と完全に同一のパイプライン**
(重力射影 → デシメーション → デトレンド → Hann窓 → FFT → 片側PSD正規化 → ドループ補償)
に通して得た `S_a(f_k)` の、**ビン2〜16 の中央値**をスカラーとして保持したもの。
単位は `(m/s²)²/Hz`。**標準偏差 σ [mG] をそのまま代入してはいけない**(次元が違う)。
中央値を使うのは、校正中に紛れ込んだ微小な振動の影響を受けにくくするため。

`m2` は v1 では使わない(周期は `m₋₁/m₀`、H1/10 は Hs の定数倍)。
スペクトル幅などの診断が必要になったら、生データログから PC 側で再計算する。

`4√m0` の直前で NaN / Inf ガードを入れる。

**なぜ S_a の段階で平均するのか**: (a) `Hs = 4√m0` は非線形で、√ は凹関数なのでセグメントごとに
Hs を出してから平均すると Jensen の不等式で系統的に過小になる。(b) ノイズ床減算を n_seg 回ではなく
1回だけ行えば、クランプによる下振れも 1回で済む。

### 感度・ノイズ床・誤差要因の実測値

以下はすべてモンテカルロまたは数値積分で確認した値。

**信号側**(スペクトルピーク成分の rms。全帯域 rms はこの約2倍):

| Hs | Tp | 鉛直加速度 rms |
|----|----|--------------|
| 1.0 m | 6 s | 27.96 mG |
| 0.5 m | 6 s | 13.98 mG |
| 0.3 m | 8 s | 4.72 mG |

**凪での見かけ Hs を作っている要因**(大きい順):

| 要因 | 見かけ Hs | 備考 |
|------|----------|------|
| デシメーションの折り返し | **0.13〜0.14 m** | ビン2〜3 に集中し ω⁻⁴ で増幅される。海況依存なので静置校正では引けない |
| ĝ 初期化誤差 25mG の過渡 | 0.126 m | 2段階初期化 + 収束するまでセグメント収集を開始しないことで対策 |
| 直線トレンド 20mG/32秒 (傾き1.1°) | 0.157 m | デトレンドで対策 |
| 直線トレンド 10mG/32秒 (傾き0.6°) | 0.078 m | 同上 |
| センサノイズ (σ=2.9mG 仮定) | 0.067 m | 静置校正値として減算 |
| 最低ビン(0.031Hz)を含めた場合の追加分 | +0.24 m | ビン1を捨てることで回避済み |

低周波の増幅率は `1/(2πf)⁴` で、f=0.03125Hz で **673倍**、f=0.0625Hz で **42.0倍**。
「数十 mG のゆっくりしたドリフト」が 1/f⁴ 除算と 4√ を通ると 1m級の Hs になる、というのが
この設計の最大の落とし穴であり、デトレンドと ĝ 過渡対策はそのための必須工程である。

**積分帯域の打切りによる系統誤差**(JONSWAP を数値積分):

| Tp | 帯域内 m0 割合 | Hs 誤差 |
|----|--------------|--------|
| 2.5 s | 0.736 | −14.2% |
| 3.0 s | 0.856 | −7.5% |
| 4.0 s | 0.951 | −2.5% |
| 6.0 s | 0.990 | −0.5% |
| 10 s | 0.999 | −0.1% |
| 12 s | 0.988 | −0.6% |
| 14 s | 0.920 | −4.1% |
| 16 s | 0.674 | −17.9% |

**既知の系統誤差として文書化するもの**: 下限ビン k1=2 では、Tp≥10秒 のときピークがビン3付近に立ち、
Hann 漏れがビン2 に落ちる。ビン2 の (2πf)⁻⁴ 係数はビン3 の 3.2倍なので漏れが過剰増幅され、
**Tp=10〜12秒 で Hs が +8% 上振れする**。

### 統計誤差と信頼度表示

`1/√(2·N_waves)` は正しい式ではない。正しくは `1/(2√(n·K_eff))`、
`K_eff = (ΣS_z)²/(ΣS_z²)` (実測 K_eff は Tp=6 で 4.03、Tp=10 で 2.29)。
加えて Hann 窓では隣接ビンのパワーが相関する(重なり係数 0.444)ため、
独立ビン仮定より分散が 1.68倍になる。

以下はモンテカルロ実測値 (Hs=1.0m, Tp=6s):

| 有効セグメント数 | 累積時間 | Hs 相対 sd | 表示 |
|----------------|---------|-----------|------|
| 1 | 32秒 | **31%**(うねり卓越で36%) | ★☆☆ |
| 2 | 64秒 | 23% | ★☆☆ |
| 3 | 1.6分 | 19% | ★★☆ |
| 6 | 3.2分 | 13% | ★★☆ |
| 7以上 | 3.7分〜 | 10% | ★★★ |

**★☆☆ の間は Hs を 0.5m 刻みで表示する**(「約 1.5m」)。★★☆ 以上で 0.1m 刻みに切り替える。
±31% の値を 0.1m 刻みで見せるのは嘘になるため。

### 体動判定

判定は2つに分離する。**波浪に伴う振動的なロールは無効化しない。**
これは「射影で吸収されるから」ではない — 周期的な `r·sin φ(t)` は線形デトレンドでも重力射影でも
除去できない実変位である(限界 (B) 参照)。**棄却しない理由は選択バイアスを避けるため**で、
荒天ほどロールが大きく、ロールで棄却すると荒天のセグメントが優先的に捨てられて
Hs が系統的に過小評価される。汚染は承知の上で受け入れ、代わりに測定位置(決定2)で抑える。

| 判定 | 指標 | 閾値 |
|------|------|------|
| 姿勢ドリフト | **セグメント始点と終点の LPF後 ĝ どうしのなす角** | **2°** (≒35 mG) |
| 高周波体動 | 1Hz ハイパス後の帯域エネルギー ÷ 積分帯域エネルギー | **0.3** |
| クリップ | `\|成分\| ≥ フルスケール − 100mG` のサンプルが1つでもある | — |
| バイブ混入 | `AccelData.did_vibrate` が1つでも真 | — |

- ĝ 角度の閾値が 15° ではなく 2° なのは、ĝ が LPF 出力だからである。
  波周波数のロールは LPF で 1/30 に減衰するので、±10° のロールでも ĝ の変化は ±0.3° にしかならない。
  15° では永久に発火しない。一方ドリフト検出としては、20mG (1.1°) で既に擬似 Hs 0.157m が出るので
  15° (=259mG) は桁が2つ緩い。
- 高周波体動を絶対値ではなく**比率**にするのは、Hs=0.5m/T=2s のチョップの差分ピークが
  Hs=1.0m/Tp=6s のうねりの13倍あり、絶対閾値ではチョップの海で全セグメントが無効になるため。
- **警告表示は 2.5秒バッチごとに即時に出す**(セグメント有効性の確定だけが32秒粒度)。
  32秒遅れて「動かないでください」が出ても行動を促せない。

```
│      1.2 m           │  ← Hs、70px前後。★☆☆ の間は「約 1.5 m」
│                      │
│                      │
│  周期 6秒  1/10 1.5m │  ← Tm-1,0(整数秒)と H1/10
│  ▓▓▓▓▓░░░  2:08      │  ← 累積有効時間
└──────────────────────┘
```

- Hs の刻みは信頼度に連動(★☆☆ = 0.5m 刻み、★★☆ 以上 = 0.1m 刻み)
- **周期は整数秒**で表示する。1セグメントでの sd が 0.57秒あるので 0.1秒刻みは嘘になる
- `Hs < 0.1 m` は「凪」と表示する(「0.0 m」とは出さない)
- 状態: 「初期化中」/「測定中」/「動かないでください」/「手を置き直してください」
- Tm-1,0 が船長から計算した T_min を下回ったら「短周期主体 — 過小評価の可能性」を出す
- 波高に応じた色分けは行わない(閾値の根拠を書けず、安全助言と読まれるため)。単色の濃淡に留める
- 未確定(有効セグメント0)の間は `--` と表示し、数字を出さない
- **バックボタンは長押しのみで終了**(ヘリに押しつけて誤爆すると累積が消えるため)

**初回起動画面**(1度だけ表示):

- 測定位置は船体の中央寄り(中心線上・前後も中央)であること
- ヘリしか無い場合は過大評価すること
- 測定中は Quiet Time を有効にすること(通知バイブがセグメントを無効化するため)

**設定画面**(別画面、初期設定時のみ):

- 船長 (追従下限周期 T_min の計算に使う。デフォルト 10m)
- 単位 (m / feet)
- 診断モード(体動判定バイパス。レベル3の既知運動テストに必須)

**設計上の要点:**

1. **`src/c/wave/` は Pebble SDK のヘッダを一切 include しない。** 同じソースを PC の gcc で
   ビルドしてテストできる。float と math.h は Pebble SDK でも使えるので制約にならない。
   64点FFT のワーキングメモリは float で 1〜2KB、アプリメモリ 128KB に対して問題ない。
2. **状態機械 (`session.c`) も純Cコアに置く。** ポーズ・再開・セグメント境界・ウォームアップ判定・
   無効セグメントの連続カウントは最もバグりやすい部分であり、ここが PC でテストできないと
   実機でしか検証できなくなる。`main.c` は「加速度バッチを session に流し、返ってきた表示状態を
   ui に渡す」だけの薄いアダプタにする。
3. **`accumulator.c` の平均は、リングバッファではなく指数移動平均で持つ。**

   ```
   S_avg ← (1 - α) S_avg + α S_new      α = 1 / min(n_seg, N_max)      N_max = 16
   ```

   `n_seg < N_max` の間は通常の算術平均と一致し、以降は実効窓長 16セグメント(8.5分)の
   指数移動平均になる。古いセグメントが等重みで残り続けて、海況が変わったのに ★★★ を
   主張する事態を防ぐ。
   **リングバッファを採らないのは、次項の persist 復元と両立しないため。**
   平均値だけからは最古セグメントのスペクトルを復元できず、復元後に押し出そうとしても
   何を引けばよいか分からない。指数移動平均なら「最古要素」の概念自体が不要になる。

4. **終了時に S_avg / n_seg / タイムスタンプを persist に保存し、10分以内の再起動なら復元する。**
   ★★☆ に必要な有効データは 96〜192秒だが、ユーザーは1分以上姿勢を保てない。
   複数回の保持にまたがる積み上げが前提である以上、アプリを閉じたら消えるのでは設計が成立しない。
   容量は S_avg (31ビン × float = 124B) + n_seg + タイムスタンプ = 約132B で、
   `PERSIST_DATA_MAX_LENGTH` (256B) に収まる。

## 手順

依存順。**テストを先に用意する**のと、**計画を覆しうる未知を着手前に潰す**のが要点。

1. **開発環境の構築(タイムボックス 2時間)**
   - `uv tool install pebble-tool --python 3.13`(ローカルの Python は 3.14 なので uv に 3.13 を取らせる)
   - `pebble sdk install latest` で SDK と ARM ツールチェーンを取得
   - 成功条件: 空アプリが emery エミュレータで起動する
   - **2時間で通らなければ Docker 分岐に切り替える。** `src/c/wave/` が SDK 非依存である以上、
     手順3〜6(作業量の約7割)は gcc だけで並行して進められるので、ここで全部が止まることはない

2. **プロジェクト雛形を整える**
   - `package.json` のターゲットを emery のみに絞る
   - `src/c/wave/` を空のスタブで作り、emery ビルドが通ることを確認

3. **【新設】実機スパイク(半日)— 計画を覆しうる未知を先に潰す**
   - 加速度の生値を 10 / 25 / 50 Hz で取得し、`APP_LOG` 経由で吸い出す最小アプリを書く
   - **(a) 実ノイズフロアの測定**: 机に静置して5分。σ [mG] を実測する。
     想定 (2.9mG) より大幅に悪ければ積分帯域の下限を見直す必要があり、
     それは決定8 の破棄と `spectrum.c` / `accumulator.c` / 全テストのしきい値に波及する
   - **(b) サンプリングレートの決定**: **100Hz(最高レート)で実船データを1回収録し、
     PC 上で各候補(10 / 25 / 50Hz への間引き + それぞれのアンチエイリアスフィルタ)を
     再現して、同一イベントに対する 0〜5Hz の差分を比較する。**
     別々の走行で 10 / 25 / 50Hz を取って比べるのでは、観測された低周波成分が
     折り返しなのか実際の波・船体運動の違いなのか判別できない。
     さらに 10Hz で収録すると、折り返しの原因である 5Hz 超の信号そのものが見えない。
     スラミングを含む区間を必ず収録対象にする
   - **(c) DataLogging API の疎通確認**: Core Devices 版 SDK で `data_logging_create` /
     `data_logging_log` が動き、10分以上の連続ログが取れるかを確認する
   - **(d) 加速度計のフルスケール実測**: クリップ判定の閾値を決めるため
   - **この3つ(a)(b)(c)が閉じるまで手順4以降の設計は確定しない**

4. **PC 側テストハーネスを先に作る**
   - `test/Makefile` で `src/c/wave/*.c` を gcc ビルドできるようにする
   - `test/synth.c`: JONSWAP スペクトル (Hs, Tp を指定) から海面変位時系列を合成し、
     2階微分して加速度時系列にする。**振幅は決定論的に `√(2S(f_k)Δf)`、位相のみ乱数、
     周波数は Δf=0.03125Hz のビン中心、RNG は固定シード。**
     (レイリー振幅で合成すると 1セグメントの Hs 推定が 21.7% ばらつき、
      正しい実装でも ±10% ゲートを3回に1回しか通らなくなる)
   - 重畳できるようにするもの: 直線トレンド、傾き(ロール角 φ(t))、**てこ腕 r による `r·sin φ(t)`**、
     水平動、体動パルス、センサノイズ、1mG量子化、クリップ

5. **コアアルゴリズムを実装 (PC 上で完結)**
   - `fft.c` → `test_fft.c`
   - `spectrum.c` (デトレンド、窓掛け、FFT、片側PSD、ドループ補償) — **S_a を返すまで**
   - `accumulator.c` (S_a の指数移動平均、固定ノイズ床減算、S_z変換、m₋₁/m₀、Hs/Tm-1,0/H1/10)
   - `test_spectrum.c` / `test_detrend.c` で検証

6. **前処理を実装 (PC 上で完結)**
   - `gravity.c` (2段階 ĝ 推定、射影、ゼロ除算ガード)、`decimate.c`、`quality.c`
   - `test_gravity.c` は **ĝ射影法と |a|法の差分試験**にする(後述)

7. **状態機械を実装 (PC 上で完結)**
   - `session.c`: ウォームアップ / 測定 / ポーズ、セグメント境界、信頼度
     (指数移動平均そのものは `accumulator.c` の責務)
   - `test_session.c` で無効区間を挟んだ非連続シーケンスを検証

8. **Pebble アプリ本体に組み込む**
   - `main.c`: `accel_data_service_subscribe(25, handler)`、手順3で決めたレートを設定
   - この時点では `APP_LOG` で値が出れば良い

9. **UI 実装**
   - 上記レイアウト。70px 数字フォントをリソースに追加(数字のみサブセット、約5kB)
   - 詰まったら `FONT_KEY_LECO_42_NUMBERS`(システム内蔵・数字専用42px)にフォールバック

10. **生データログ**
    - **10Hz(または手順3で決めたレート)の生3軸 int16** をセグメントごとに保存
      (320点 × 3軸 × int16 = 1920B/セグメント、10分で約36kB)
    - メタデータに **N̂(そのセグメントの高周波帯パワー)を必ず含める**
    - デシメーション後や射影後のデータでは、エイリアスも ĝ 推定バグも事後に切り分けられない

11. **設定画面**
    - 船長、単位 (m/feet)、診断モード。persist で保存

12. **エミュレータ検証**
    - `test/gen_emu_accel.c` で合成波の CSV を生成し `pebble emu-accel custom --file` で注入
    - **CSV には z軸に −1000mG の重力オフセットを重畳する**(無いと `|ĝ|=0` でゼロ除算)
    - **注入レートが実時間と一致するかをここで確認する。**
      一致しない場合、この層で確認できるのは「クラッシュしないこと」「UI の描画」だけになるので、
      そのときのチェックリストを別途用意する(数値検証は PC テストが担うので致命傷ではない)

13. **実機: 既知運動テスト**
    - **診断モード(体動判定バイパス)を有効にする。** 手で振る動作は高周波体動判定に必ず引っかかるため、
      バイパスなしではこのテスト自体が実行できない
    - メトロノームに合わせて手で一定周期・一定振幅に上下させる

14. **実海域テスト**
    - 小型船上で、**船体中央寄りの固定物**に手か時計を置いて測定
    - 可能なら**ヘリでも測って差を見る**(てこ腕の影響を実測する)
    - アプリの Hs / Tm-1,0 と生データログを記録
    - 同時刻・近傍の NOWPHAS 観測点または気象庁沿岸波浪予報と突き合わせる

### レベル3: 実機の既知運動

**前提: 診断モード(体動判定バイパス)を有効にすること。**

| 手順 | 期待 |
|------|------|
| 机に静置して5分 | Hs < 0.1m。**この静置データを本番と同一パイプラインに通して片側PSD を求め、ビン2〜16 の中央値を `N_floor` [(m/s²)²/Hz] として persist に保存する。** σ [mG] をそのまま代入してはいけない(次元が違う) |
| メトロノーム 30bpm (周期4秒)、**片振幅 10cm**(上下の全ストローク 20cm) | Hs = 2√2 × 片振幅 = **0.283 m** の ±30%。周期 4秒 ±0.5秒 |
| メトロノーム 20bpm (周期6秒)、片振幅 10cm | Hs = 0.283 m の ±30%。周期 6秒 ±0.5秒 |
| 周期2秒(帯域上端)で同上 | 参考値。Hann漏れ −6.7% とデシメーション減衰 −9.6% で **−15.6% の系統誤差**が出るのが正常 |
| 診断モードを切って手を動かす | 「動かないでください」が **2.5秒以内**に出る |
| 静置で1時間放置 | **バッテリー消費 ≤10%/時**。超える場合は表示スリープ(10秒無操作で画面更新停止、加速度購読は継続)を追加する |

### レベル4: 実海域 (本番の検証)

1. 小型船で、NOWPHAS 観測点の近傍または沿岸波浪予報の対象海域に出る
2. **船体中央寄りの固定物**に手か時計を置き、★★☆ 以上になるまで積算する
3. 可能なら**同じ海況でヘリでも測り、両者の比を記録する**(てこ腕の実測)
4. アプリの Hs / Tm-1,0、時刻、位置、体感を記録。生データログも保存
5. 帰港後、同時刻の NOWPHAS 実測値(または予報値)と突き合わせる

**合格条件**:

**±40% の定量判定に使ってよい参照値は、十分近接した同時刻の NOWPHAS 実測値のみ。**
沿岸波浪予報は使えない。背景 (5〜7行目) で述べたとおり、予報は広域・時間粗で目の前の海況と
一致しないことがこのアプリを作る理由そのものであり、
一致しなかったときにアプリと予報のどちらが外れたのか決定できないため。
予報との比較は**参考記録に留め、正式な検証回数には数えない**。

- 通常海況 (NOWPHAS 実測 Hs ≥ 0.3m): アプリの Hs が観測値の **±40% 以内**
- 凪 (NOWPHAS 実測 Hs < 0.3m): **アプリの Hs < 0.3 m** という片側条件のみ。
  Hs=0.1m/Tp=10s は SNR(パワー)=1.28 しかなく、バイアスだけで +20% 乗るので ±40% には収束しない
- **全体条件: 3回の測定でアプリ Hs と参照 Hs の順序関係が一致すること。**
  ±40% だけだと、常に 1.0m を返す実装が参照値 0.71〜1.67m を全部通してしまう。
  この順序関係の条件だけは、参照が予報値でも相対比較として成立する

**NOWPHAS 観測点の近傍に出られない場合、レベル4 の定量検証は成立しない。**
その場合は「順序関係の条件のみ確認し、定量精度は未検証」と正直に記録する。

**異なる海況(凪 / 0.5m級 / 1.5m級)で最低3回実施する。**

外れた場合は生データログを `tools/decode_log.py` で PC に吸い出し、以下を切り分ける:
体動が混じっていたか / N̂ が静置測定値の3倍を超えていないか(エンジン振動) /
スペクトルのピークが帯域端に張り付いていたか / ロール由来のてこ腕成分か / 船の追従性の限界か。

**系統差の注記**: NOWPHAS が報じるのは零交差法の H1/3、本アプリが出すのは Hm0 = 4√m0。
両者は一般に 5〜10% 異なる(浅海・広帯域で Hm0 > H1/3)。±40% には十分収まるが、差の向きは既知。

## 却下した案

| 案 | 却下理由 |
|----|---------|
| **高周波帯からのノイズ床その場推定** | **原理的に不可。** 波の加速度スペクトルは `S_a = S_η(2πf)⁴` で、JONSWAP の f⁻⁵ 尾に f⁴ が掛かるため **S_a ∝ f⁻¹** となり高周波でもほとんど落ちない。0.8〜1.0Hz にあるのはセンサノイズ (1.68 mG²/Hz) の **1680倍の波由来の実信号** (2824 mG²/Hz)。これを減算するとモンテカルロで Hs が **−25%**、sd も 32%→50% に悪化した。SFY ブイが採っているのも減算ではなく低域カットオフである |
| **時間領域法** (バンドパス+2回積分+ゼロクロス) | 素朴な二重積分は発散する。安定 IIR で書けば発散はしないが、fc=0.06Hz で整定に 15〜25秒かかり 32秒セグメントの半分を潰す。**最大の理由は、スペクトルが残らないので実海域での事後切り分けができないこと** |
| **周波数領域+時間領域の併用** | Hmax を実測できる利点はあるが実装が約1.5倍。H1/10 を採用したので不要になった |
| **最大波高 Hmax の表示**(累積時間依存) | N波中の最大値なので、海況が一定でも積算するだけで表示が **+46% 単調増加**する(32秒で1.05m → 384秒で1.53m)。ユーザーが「波が高くなってきた」と誤読する。継続時間非依存の H1/10 = 1.27Hs に変更 |
| **ピーク周期 Tp (argmax + 3点重心補間)** | argmax は各ビンの自由度2カイ二乗のばらつきの中でビン間を飛ぶので、重心補間しても値が飛ぶ。1セグメントで sd 1.00秒。Tm-1,0 はほぼ同じ値域で sd 0.57秒 |
| **船種を問わない汎用アプリ** | 大型船では過小評価するため「波の高さを知りたい」という目的に直結しない |
| **船長を設定して RAO 補正** | RAO は船形・荷重・進行方向・造波方向で変わる。船長だけの補正は根拠が薄い。船長設定は**補正には使わず、追従下限周期 T_min の計算と警告表示にのみ使う** |
| **加速度ベクトルの大きさ \|a\| を鉛直加速度の代用にする** | 水平加速度が `a_h²/(2g)` で漏れる(水平100mGで5.0mG、周波数は2倍)。小型船は横揺れが大きいのでこれが効く |
| **128秒窓・数分の連続測定** | 「1分以上体勢を維持するのは難しい」というユーザーの制約により棄却 |
| **一発測定 (ボタン→32秒→確定)** | 誤差が常に 31% に固定される。積み上げなら 7セグメントで 10% まで下がる |
| **船のヘリに手を置く**(当初案) | ロールのてこ腕が最大の位置で、全幅3m・ロール15°なら真の Hs=0.5m が **1.22m (2.4倍)** と出る。重力射影では原理的に消せず、ジャイロが無いので分離もできない。測定位置を船体中央寄りに変更した |
| **積分帯域を周期32秒まで広げる** | 最低ビンの増幅が 673倍で、凪でも Hs 0.24m が出る。かつ32秒セグメントで32秒周期の波を見るのは原理的に無理 |
| **測定結果の履歴保存** | v1 スコープ外。ただし**終了時の累積状態の persist 保存は別途必須**(積み上げ式が成立しなくなるため) |
| **バックグラウンド継続測定 (ワーカー)** | 「手を置いている間だけ積算する」設計なので意味が薄い。ワーカーはメモリ制限も厳しい |
| **JavaScript SDK (Alloy) での実装** | Developer Preview でセンサー API が未確定 |
| **波高に応じた色分け(緑/黄/赤)** | 閾値の根拠が書けず、事実上「安全/危険」の助言になる。5mの船と12mの船で同じ 1.5m を赤にする根拠がない |

## 未解決の論点

1. **`pebble emu-accel custom --file` の注入レートが実時間と一致するか**
   一致しないとエミュレータでの数値検証が意味を成さない。手順12で確認し、
   駄目ならエミュレータの役割を「UIと状態遷移の確認」に限定する
   (数値検証は PC テストが担うので致命傷ではない)。

2. **DataLogging が使えなかった場合のフォールバック**
   手順3(c) で判明する。使えない場合:
   - **persist 案は不可**: 1レコード 1920B 超に対し `PERSIST_DATA_MAX_LENGTH` は 256B。
     分割しても総容量 4KB では 2セグメント分しか入らない
   - **残る手段は `src/pkjs/index.js` 経由の `app_message` リアルタイム送信**。
     実海域テストにスマホを持参する運用になる。BT 切断時の再送設計が必要
   - この場合、手順10 のスコープが pkjs 側に広がる

3. **実ノイズフロアが想定より悪かった場合の積分帯域の再調整**
   手順3(a) で判明する。下限をビン3 (0.094Hz) に上げると、**Tp=12秒 で −26.2%、
   Tp=10秒 で −5.5% の系統誤差**が入る(実測)。
   単に「長周期が測れなくなる」のではなく、**警告なしに26%小さい値を出し続ける**ので質的に悪い。
   下限を上げるなら、同時に「長周期のうねりを検出したら測定範囲外を表示する」ロジックが必要。

4. **デシメーションの折り返しが凪の floor を決めている件**
   5点箱型平均は 2/4/6/8Hz に厳密な零点を持ち、間引き率5のエイリアス中心と一致するので、
   **折り返し抑圧そのものは十分**(Hs への寄与は +0.1〜4.4%)。
   問題は、折り返し由来の m0 (1.0〜1.3e-3 m²) がセンサノイズ由来 (2.8e-4 m²) の 3〜5倍あり、
   ビン2〜3 に集中して ω⁻⁴ で増幅され、凪での見かけ floor を **0.13〜0.14m** に押し上げること。
   海況依存なので静置校正では引けない。手順3(b) で 1.5〜2.5Hz 帯を実測してから判断する。

5. **測定位置を中央寄りに変えたときの実用性**
   船によっては中央寄りに手を置ける固定物が無い。その場合ヘリに戻ることになり、
   てこ腕の過大評価を受け入れることになる。手順14 で両方の位置で測って比を実測し、
   「ヘリで測った場合の補正係数」を経験的に出せるかを判断する。

6. **航走中の遭遇周期**
   航走中は遭遇周波数 `ω_e = ω + ω²V/g` により、表示される周期が真の波周期とずれる。
   10ノットで真の Tp=6秒なら、向かい波で 3.87秒 (−35%)、追い波で 13.3秒 (+122%)。
   Hs 自体は船が受ける鉛直運動のエネルギーなので保たれるが、周期は別物になる。
   **v1 は「漂泊(エンジン停止または微速)を前提とする」と README に明記して回避する。**
   航走中も使えるようにするかは v2 の論点。

## 参考にする先行実装

同じ問題(組み込みマイコン上で加速度から波浪諸元を出す)を解いた公開実装が2つある。
少なくとも (a) 低周波カットオフの扱い、(b) サンプリングレートの選択、(c) デトレンドの有無
の3点は、これらに合わせる。

- **OpenMetBuoy-v2021** (Rabault et al., Geosciences 2022) — Cortex-M 上で
  「加速度 → 鉛直成分抽出 → スペクトル二重積分 → Hs/Tp」を実装した完全なオープンソース事例。
  鉛直成分抽出に 30秒 LPF ではなく **AHRS カルマンフィルタ(クォータニオン)** を使い、100Hz で処理している。
  https://www.mdpi.com/2076-3263/12/3/110
- **SFY wave buoy** (arXiv 2401.02286) — 低周波カットオフの自動決定法
  (0.05Hz 以上の最初のスペクトル極小をカット点にする)と、サンプリングレートに関する知見
  (衝撃イベントのアンダーサンプリングが低周波ノイズを生む)を持つ。
  https://arxiv.org/html/2401.02286
- **SYLT-FFT** — Pebble で実績のある整数FFT。今回は 64点 float なので自前実装(約60行)のほうが
  小さくテストも容易だが、詰まったときの参照先として。 https://github.com/stg/SYLT-FFT

## 実装記録 (2026-09-06)

手順1〜2、4〜12 を実施した。手順3(実機スパイク)と手順13〜14(実機・実海域)は実機待ち。

### プランの想定が外れた点

**(1) Hann 窓漏れの補正が必須だった。プランの「+8%」は大幅な過小評価。**

実測すると、下限ビン k1=2 での漏れバイアスは Tp=4s で +4%、**Tp=10s で +19%**
(プラン記載は +8%)。原因は、Hann の隣接ビン漏れが `1/(2πf)⁴` の急峻な重み勾配で
非対称に増幅されること。低周波側へ漏れた分は重みが大きく、高周波側へ漏れた分は小さいので、
差し引き常に過大評価になる。ビン2 とビン3 の重み比は 5.06 倍ある。

対策として **積分の重みを窓のカーネルでデコンボリューションする**方法を実装した
(`accumulator.c`)。非コヒーレントな漏れは `S_obs = K·S_true`、`K = tridiag(1/6, 2/3, 1/6)`
と書けるので、`w'' = K⁻¹w` を積分の重みに使えば真値が復元される。K は対称・三重対角・定数なので
起動時に Thomas 法で1回解くだけで済む。

Tikhonov 正則化(λ=0.1)を加えると、周期 4〜12秒でバイアスが **±2.5% 以内**に収まり、
1セグメントのばらつきも 19.0% → 17.8% とわずかに改善した(補正は堅牢性を犠牲にしない)。

**(2) 重力推定のウォームアップは IIR ではなく単純平均でなければならない。**

ここで2回間違えた。記録しておく価値がある。

- **「方向が動かなくなったら収束」という判定は、船の上では永久に成立しない。**
  結果として τ=2s の速い時定数が使われ続け、**ĝ が波そのものに追従してしまう**
  (0.0625Hz でゲイン 0.79)。実測でロール振幅によらず Hs が **−15%**。
- **速い IIR で初期化すると、ĝ が収束中に吸収した水平成分(最大 111mG)を保持し続ける。**
  遅い時定数はそれを自分の時定数でしか放出しないので、その間ずっと水平動が射影に直接漏れる。
  **τ_slow を長くするほど悪化する**という直感に反する挙動になり、
  水平動 100mG@0.0625Hz でのバイアスは τ=30s の +5% から τ=240s では **+40%** に増えた。

正解は **固定窓の単純平均**。応答が sinc になるので、16秒窓なら 0.0625Hz
(積分帯域の最下端、かつ `1/f⁴` が最も効く周波数)に**厳密な零点**が立ち、
0.125Hz にも零点が立つ。実測で settle 後の残留水平成分は 283mG の入力に対し **0.0mG**。

この修正で、水平動 200mG@0.0625Hz でのバイアスは射影法 **−2.5%** に対し
|a| 法 +26.4% となり、**決定5(重力射影)の優位性が10倍の差で実証された**。
修正前は逆に |a| 法のほうが良く見えており、実装の欠陥が設計判断を覆しかけていた。

**(3) 単一シードでの検証は無意味だった。**

1セグメントの Hs は sd 31% でばらつく。手法比較を単一シードで行うと、
比較したい効果(数%〜数十%)がばらつきに完全に埋もれる。実際、修正前の測定で
「ベースラインが −14.4%」という系統誤差が見えたが、24シード平均では −2.7% だった。
以降の測定はすべて 20〜24シードの平均で行っている。

**(4) `test/Makefile` にヘッダ依存が無く、構造体変更でスタックスマッシュが起きた。**

`wave_gravity` のフィールドを入れ替えたとき、一部のオブジェクトが再コンパイルされず、
古いレイアウトのままリンクされた。コンパイルエラーにはならず実行時に落ちる。
`-MMD -MP` と `-include $(OBJS:.o=.d)` を追加して修正済み。

### 未解決の論点の解決状況

**論点1(`pebble emu-accel` の注入レート)— 解決。エミュレータでの数値検証は不可。**

## 実機での結果 (2026-09-07)

実機 (Pebble Time 2) にインストールして判明したこと。**未解決論点3と4はここで解決した。**

### 実ノイズフロア (論点3) — 想定の 6.9倍だった

オンウォッチ校正が返した値は **1.116e-3 (m/s²)²/Hz**。
プランの試算 (σ=2.9mG 前提) は 1.62e-4 だったので **6.9倍**、
σ に直すと **約 7.6mG** (想定 2.9mG の 2.6倍)。

ホスト側で σ=7.6mG を入れて校正を再現すると 1.058e-3 が出て実測とほぼ一致したので、
このノイズモデルは検証できたとみなせる。

### 積分帯域の再調整 (論点4) — 不要だった

論点4は「ノイズが想定より悪ければ下限をビン3に上げる必要があり、
その場合 Tp=12秒 で −26% のバイアスが入る」としていた。
**実際にはノイズが 6.9倍でも帯域を狭める必要はなかった。**

σ=7.6mG・校正後のホスト実測:

| 真の Hs | 測定値 |
|---------|--------|
| 静置 (0) | **0.048 m** → 表示は「calm」 |
| 0.3 m | 0.297 m (−1%) |
| 0.5 m | 0.493 m (−1%) |
| 1.0 m | 0.986 m (−1%) |

帯域を狭めずに ±1% を保っている。論点4 は閉じる。

### 代わりに直したもの: ビンごとのクランプ

実機は静置で **Hs 0.10〜0.16m**、しかも周期が 15秒 (=ビン2) に張り付いていた。
原因は `resid = max(0, s_avg - noise_floor)` の**ビンごとのクランプ**だった。

ノイズは床の周りで正負にばらつくので、負の側を捨てて正の側だけ残すと、
**ノイズの約半分が信号として残る**。しかもそれが最低ビンに集中するため、
`1/f⁴` の重みが最も大きいところで増幅される。

符号付きのまま合計し、`m0` に対して一度だけ非負を保証する形に変更した。
これで正負が相殺される。

### それでもゼロにはならない — 表示閾値が必要な理由

クランプを外しても静置が 0 にはならない。`m0` の期待値が 0 でも実現ごとに
正負にばらつき、負は「結果なし」として扱われるので、`Hs = 4√m0` の平均は
常に正に残る。ホスト実測で 0.02〜0.06m (ノイズレベル依存)。

プランの UI 仕様にあった「`Hs < 0.1 m` は凪と表示」は**まさにこれへの対策**だったが、
実装が漏れていた。実装して解決。周期・1/10・短波警告も同時に抑制する
(ノイズ床と区別できない読みに対しては、いずれも意味を持たない)。

### 実機で判明したその他の欠陥

| 症状 | 原因 | 対策 |
|------|------|------|
| 20秒で App fault (3回、すべて `__ieee754_sqrtf` の同一オフセット +0x76) | 実機で libm の内部データポインタが使えない。再配置エントリは ELF に存在し、エミュレータでは動く | libm を排除し `wave/fastmath.c` を自前実装。副産物として RAM 32.8KB → 21.0KB |
| 測定が完了しない (57秒で Levelling に戻り seg=0) | 姿勢変化検出が「35°逸脱が1秒継続」で発火。**腕を上げて画面を読む動作がちょうどそれに当たる** | 継続時間を 4秒に延長 |
| 文字が小さい | LECO_42 を使っていた | LECO_60 (システム最大) に。周期と1/10は2行に分割 |

なお `sqrtf` のクラッシュ調査では、私の仮説が2回外れている
(スタックオーバーフロー、LECO フォント欠落)。決定打になったのは
「3回のクラッシュがすべて関数内の同一オフセットだった」ことと、
「追加したトレースが1行も出なかった=セグメント完成前だった」こと。
